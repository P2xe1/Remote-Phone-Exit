**一台手机 = 一个出口。** 它在哪个网络里，你的流量就从哪个网络出去——不需要服务器，不需要公网 IP，不需要端口映射。

```
大陆代理 ──▶ Cloudflare ──▶ 隧道 ◀─▶ 海外终端连接的WiFi ──▶ 目标网站
大陆代理 ◀── Cloudflare ◀── 隧道 ◀──  海外终端连接的WiFi ◀── 目标网站
```

终端设备侧只装两个程序：一个接住从隧道送进来的流量、用所在宽带直连目标，另一个把回程隧道主动连出去并保持在线。你在终端上的代理软件里填好配置、连上它，出口就成立了。

另附一个实时监控大屏，把「客户端 → Cloudflare 边缘 → 隧道 → 海外终端设备 → 目标网站」整条链路拆开逐段测量；哪一段出了问题，第 10 秒就能看出来。它实时展示这些内容：

- **分段延迟**：客户端→边缘、边缘→隧道、隧道→设备、设备→出口，四段各自实测，再加一条端到端总延迟；哪一段抖了、卡了，直接看那一段。
- **带宽与峰值**：实时上下行速率、15 分钟滑动峰值、当日峰值，配 15 分钟滑动波形与带宽仪表盘，能看出是"一直慢"还是"刚才冲高"。
- **在线用户与流量**：每个用户的连接状态（在线传输中 / 离线断开多久 / 从未连接）、实时速率、订阅拉取次数，以及按人累计的流量榜（下行 / 上行分开统计）。
- **设备侧遥测**：终端设备的电量与温度、WiFi 名称与信号强度、链路速率、内核运行时长、活跃连接数、隧道错误数——出口那一端健不健康，一眼可见。
- **数据可信度**：页面直接标注数据新鲜度（"几秒前数据"），刷新节奏可选 10 秒极速或 1 分钟采集；任何一项测不到就显示 `--`，绝不填假数字。

### 从零到跑通

**完整清单见 [`docs/ZERO_TO_RUNNING.md`](docs/ZERO_TO_RUNNING.md)** —— 六步，每步都写了"在哪做、怎么验证"。
最短路径（前置：域名已托管到 Cloudflare、电脑装好 Python 3 与 Node.js、设备能被 adb 识别）：

```bash
cp .env.example .env                 # 1) 按 .env 里的注释填好各项
python deploy/gen_secrets.py         # 2) 占位口令 -> 强随机值（只改仍是占位的项）
python deploy/一键.py all             # 3) 密钥 -> 取二进制 -> 体检 -> 部署边缘 -> 推节点 -> 验收
sh /data/local/tmp/install_node.sh   # 4) 设备侧：体检 -> 启动 -> 复查进程
```

两条最容易被忽略、少了就起不来的命令：

| 命令 | 作用 |
| --- | --- |
| `deploy/fetch_binaries.py` | 从官方源取**代理核心**与**隧道客户端**，校验后推到设备（仓库不带这两个二进制） |
| `deploy/gen_secrets.py` | 生成管理口令 / 同步密钥 / UUID；不生成的话口令会停留在示例值上 |

## 它解决什么问题

机房 IP（云服务器）在各类风控模型里天然处于劣势；住宅宽带 IP 通常更"干净"。本项目的目标很明确：

**让客户端的流量，最终从一个真实的海外住宅宽带公网 IP 出去。**

围绕这个目标才有了下面这些取舍：出口必须是住宅、设备在别人家里必须能自愈、国内入口必须借任播网络 + HTTPS 伪装、家庭上行带宽要省、监控必须可信。

## 架构一览

```
用户端 ──HTTPS(443, VLESS+xhttp+TLS)──▶ Cloudflare 边缘 ──反向隧道──▶ 住宅节点 ──▶ 公网
(Clash/                              │  · Worker：订阅下发 / 遥测聚合 / 大屏      (Xray + cloudflared)
 v2rayN…)                            │  · Argo 智能路由（免公网入口、免证书维护）  · 8 个采集脚本
                                     │
                                     └──◀── 遥测：节点每 ~6 秒主动上报
```

| 角色 | 职责 | 挂了会怎样 |
|---|---|---|
| 用户端客户端 | 封装流量、按规则分流、发往优选接入地址 | 只有该用户断 |
| Cloudflare 边缘 | 就近接入、伪装、订阅与遥测聚合、大屏 | 系统级不可用 |
| 住宅节点 | 代理核心、隧道、全部测量脚本 | 全员断网 + 大屏数据冻结 |
| 监控大屏 | 把边缘上的快照渲染成人能看懂的状态 | 只是"看不见"，链路照常 |

## 快速开始

### 0. 前置条件

- 一个 Cloudflare 账号（免费额度即可）
- 一个域名，DNS 交给 Cloudflare
- 一台接入家庭宽带的常驻设备（旧手机 / 迷你主机 / 软路由）
- 本机装好 Python 3 与 Node.js（Node 仅用于部署前语法检查）

### 1. 准备配置

```bash
cp .env.example .env      # 填入你自己的值
```

必须填：`CF_API_TOKEN`、`CF_ACCOUNT_ID`、`CF_KV_NAMESPACE_ID`、`CF_SCRIPT_NAME`、
`WORKER_HOST`、`TUNNEL_HOST`、`ADMIN_PASSWORD`、`SYNC_SECRET`、`VLESS_UUID`。
每项含义都写在 `.env.example` 的注释里。

### 2. 部署边缘

**方式一：一键菜单**（推荐，含体检 → 部署 → 验收）

```bash
python deploy/一键.py
```

> ⚠ 必须用 `deploy/一键.py`。仓库根目录**没有**一键入口 ——
> 菜单靠自身所在目录定位各步骤脚本，放到别处就找不到步骤文件了。

**方式二：手动分步**（想看清每一步时用）

```bash
node --check edge/worker_deploy.js       # 1. 先语法检查（可选）
python deploy/step1_check.py             # 2. 环境体检：配置/令牌/域名/设备
python deploy/step2_deploy_edge.py       # 3. 部署边缘（填节点地址 + 注入版本 + 上传）
python deploy/step4_verify.py            # 4. 线上验收（等 20~30 秒再做）
```

判定成功的标准：**三处版本号一致** —— 源码里的、`/api/live` 返回的、页面内嵌的。

**关于 `tools/cf_deploy.py`**：它现在只是**兼容包装器**，会把参数转交给
`deploy/step2_deploy_edge.py`。不要再往它里面加部署逻辑 —— 两套实现必然漂移，
历史上就因此部署出过带占位符的 Worker。配置一律从 `.env` 读，不从命令行传令牌。

### 3. 部署住宅节点

把 `phone/scripts/` 推到设备上（例如 `/data/local/tmp/`），然后：

```bash
sh /data/local/tmp/run_daemon.sh              # 完整重启（先杀旧进程再拉起）
```

> 三条铁律：**改完脚本必须重启进程**；**行尾必须是 LF**；**重启顺序不能错**（先杀看门狗）。

### 4. 打开大屏

```
https://<WORKER_HOST>/admin?pwd=<ADMIN_PASSWORD>
```

## 数据与状态放在哪（本项目最重要的设计）

边缘是分布式的，而键值存储免费配额很紧（**写入每天只有 1000 次**）。所以状态分三层：

| 层 | 可见范围 | 放什么 |
|---|---|---|
| 实例内存 | 单个实例 | 只做加速，随时可丢 |
| 机房缓存 | 同机房所有实例 | **"一个请求写、另一个请求读"的状态全放这里**，且写入必须 `await` |
| 全局存储 | 全球一致 | 只有必须全球一致的权威数据（用户库、单键指令） |

把写入压到极限的四种手法：**结构性隔离**（写只存在于极少数函数）、**变更熔断**（内容没变不写）、
**读取边缘缓存**、**写入预算保险丝**。

## 监控的五个采集面

| 采集面 | 回答的问题 | 频率 |
|---|---|---|
| 遥测上报 | 节点本身还好吗（电量/温度/网络/连接数/流量） | 约 6 秒 |
| 接入点时延与丢包 | 流量从哪个接入点进去最快最稳 | 60 秒一轮 |
| 节点 → 边缘 RTT | 链路"腰部"现在怎么样 | 15 秒 |
| 中转节点巡检 | 每个节点通不通、多快、实际落在哪 | 10 秒 1 个 |
| 手动全速扫描 | 现在立刻要一份最新完整结果 | 按需 |

### 三条口径纪律

1. **同一个数字只有一种口径** —— 单次往返与两次往返不能混着比。
2. **无效样本要丢弃，规则写死** —— 例如低于 10 ms 的样本一律作废。
3. **测不到就显示"未测到"** —— 绝不兜底填充。

> 第 3 条是红线。一旦允许"猜一个值填上"，监控就从"事实"退化成"叙事"，
> 真实故障会被漂亮的数字盖住。项目历史上就吃过这个亏：探测失败时回填时间戳，
> 把"从未测到"伪装成"刚测过"，大屏长期显示骗人的绿色。

## 排错：先二分，再深入

| 现象 | 先查 |
|---|---|
| 全部节点超时 | 客户端是否缺浏览器指纹参数（"全挂"的典型原因） |
| 只有个别节点超时 | 该接入地址是否失效 → 换节点 |
| 大屏所有数字冻结 | 节点上报脚本是否在跑、隧道是否存活（看"数据年龄"） |
| 节点矩阵数据陈旧但文件时间在变 | 去重逻辑是否写成了"保留第一条" |
| 同一份用户名单在不同入口不一致 | 权威数据是否被放在了实例内存/机房缓存里 |
| 点"手动刷新"没反应 | 指令是否被写、被取走、被回执（不能"读取即删"） |
| 探测频率翻倍 / 资源异常 | 同一脚本是否跑了两份以上 → 需要单实例锁 |

更多现象与定位方法见教程第 12 章。

## 设计约束（改代码前先读）

1. **配额是天花板**：任何"顺手加个周期性请求"的想法，先算它一天产生多少次。
2. **家庭带宽与电量有限**：探测/心跳共享同一条上行，能合并就合并、能降频就降频。
3. **分布式没有全局内存**：跨机房要一致，就必须有全球权威源。
4. **一个指标只出现一次、只写一个来源**：重复展示 = 迟早自相矛盾。
5. **改动前先备份，并且知道怎么回滚**：所有部署器都会自动留回滚点。
