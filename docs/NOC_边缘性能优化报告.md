# NOC 边缘性能优化报告 · 用户库读取路径重构

- 时间：2026-10-03 12:12（某地时间）
- 线上版本：Worker **#81**
- 起因：遥测卡片修复后暴露出 `serverMs`（CF 边缘处理耗时）中位 **170ms** 偏高

---

## 一、根因定位

用 `/api/rtt`（不做任何工作的纯探针）作基准对照，发现：

```
serverMs 采样: 204, 229, 125, 184, 83, 60, 86, 170   (中位 170ms)
且此时 data = 0 条  →  耗时与数据聚合无关
载荷构成: 总 5333 字节 (history15m 1792 / users 1706 / userTraffics 791)
```

**病根**：`getCachedUsers()` 的顺序是「isolate 内存 → **KV** → Cache API」。

- isolate 内存 TTL 只有 20 秒
- 低频站点的请求**分散落在不同 isolate / 不同机房**上，每个新 isolate 内存都是空的
- 于是**几乎每次请求都要真读一次 KV**（50~200ms）

---

## 二、修复方案

### 关键修正：单纯提高 TTL 是无效的
最初想直接把 `USERS_MEM_TTL` 从 20 秒提到 120 秒，但**这解决不了问题** ——
新 isolate 的内存永远是空的，TTL 再长也命不中。

### 实际采用的三层结构

```
① isolate 内存        (120 秒)          最快, 但只在同一 isolate 内有效
② 本机房 Cache API    (120 秒有效期)    ★ 关键: 免费无限, 同机房所有 isolate 共享
③ KV noc:users:master (全局权威源)      只在②未命中时读, 读后回填②
```

把**免费的 Cache API 提到 KV 之前**当快路径。缓存条目带**有限 max-age**，
到期自然失效 → 下次请求回源 KV → **一致性仍由 KV 保证**。

### 顺带发现并避免的两个陷阱

**陷阱 1（数据丢失风险 · 已避免）**
快路径会让后台读到最长 120 秒陈旧的用户库。若后台**增删改**基于陈旧数据再写回，
**会把别的机房刚做的改动直接覆盖掉**。
→ 因此新增 `getAuthoritativeUsers()`，**强制后台写入与页面渲染直读 KV、不加任何缓存**。

**陷阱 2（缓存无限续期 · 已避免）**
`touchUser()` 原本每次 `/sub` 拉取都把整个用户库写回 Cache API。
在快路径下，这会让**已过期的数据被无限续期**，永远等不到回源 KV，一致性彻底失效。
→ 改为**只更新 isolate 内存，不写 Cache API**。

### 调用点分流

| 端点 | 每天调用 | 读取方式 | 理由 |
|---|---|---|---|
| `/api/report_traffic` | **14,400** | 快路径（Cache API） | 高频，省 CPU 与 KV 读 |
| `/sub` | 高频 | 快路径 | 同上 |
| `/api/stats_data` | 1,440 | 权威 + `.cacheTtl:30` | 会重渲染用户表，不能太陈旧 |
| `/api/phone_users`（读/写） | 低频 | **权威（无缓存）** | 写入正确性必需 |
| `/api/phone_xray_config` | 低频 | **权威（无缓存）** | 下发给手机的配置必须准 |
| `/admin`（页面 + 增删改） | 极低频 | **权威（无缓存）** | 管理界面必须立刻看到真实结果 |

## 三、实测效果

### 高频路径：服务端耗时降到 ≈ 0

以 `/api/rtt` 纯探针为基线（仅网络+握手），比较各端点的额外服务端耗时：

| 路径 | 中位耗时 | 相对基线之差 |
|---|---|---|
| `/api/rtt`（基线） | 202 ms | — |
| **`/api/report_traffic`** | 201 ms | **−2 ms ≈ 0** ✅ |
| **`/sub`** | 154 ms | **−48 ms ≈ 0** ✅ |

**结论：每天 14,400 次手机上报路径的服务端处理成本从约 140ms 降到 ≈0**，
折合约 **每天省下 34 分钟 Worker CPU**，该路径的 KV 读取降到 0。

### 大屏接口

| 机房状态 | serverMs |
|---|---|
| 冷机房（首次访问） | 139 ~ 201 ms |
| **热机房（30 秒缓存命中）** | **54 ~ 58 ms** |

低频站点每次请求常落到不同机房，所以冷机房偏多；但大屏每 60 秒才轮询一次，
139ms 完全无感。

## 五、已知取舍

- **单机房最多陈旧 120 秒**（后台页面与大屏接口实际更短：后台=实时，大屏≤30 秒）
  —— 已确认此延迟可接受。
- 大屏接口 `serverMs` 仍会有 54~200ms 的波动，这是**低频站点冷机房的固有成本**，
  已通过显示真实值让它可观测，而不是掩盖。
- `lastSeen` / `pullCount` 现在只在 isolate 内存中更新，不再跨 isolate 共享
  —— 属展示字段，不影响任何功能（在线状态与流量均来自手机实测上报）。
