# 在线时刻与在线状态「跨机房不一致」修复报告

> 日期：2026-10-05（第二轮）
> 影响面：运营大屏「用户连接状态」板块 + 用户管理表的状态列
> 线上版本：修复后部署版本 `b<日期>-<时间>`
> 处置原则：**不造假** —— 没有权威来源时宁可显示 `--` / `从未连接`，绝不编一个数字

---

## 0. 一句话结论

大屏上「某某 刚断开 · 几分钟前在线」这块，**以前不是"观测结果"，而是"各机房各自的推算结果"**。
同一个用户被不同的机房算出不同时间，就会出现两种你见过的怪现象：

1. **好几个人显示的时间一模一样**（都被同一批旧数据盖了同一个时间戳）；
2. **同一个人刷新一次变一个时间**（这次请求落到了另一个机房）。

根因是三条 bug 叠加，不是单点故障。下面逐条讲。

---

## 1. 用户看到的现象

| 现象 | 例子 |
|---|---|
| 多个离线用户时间完全相同 | 4 个人同时显示「1 分钟前在线」 |
| 同一个人刷新后时间变了 | 一会儿「10-03 20:07」，一会儿「1 小时前」 |
| 同一块卡片自相矛盾 | 左边写「长期离线 2 天前在线」，右下角时刻却写着今天 |
| 管理表与状态板块打架 | 板块写「长期离线」，旁边的表格却全绿「🟢 在线待命」 |
| 明明没人在线，却显示一堆在线 | 从境外机房读接口，6 个早已离线的用户全被判成「在线」 |

---

## 2. 根因（三条叠加 + 一条派生）

### 根因 ①：手机读「谁在线」的正则在找一个不存在的字段

节点脚本需要向连接核心要"当前活动连接名单"。原来按 `"user": "..."` 这种写法去匹配，
而连接核心实际返回的结构是**一个数组**：

```
{"users":["user>>>user_<令牌>>>online", ...]}
```

于是**匹配永远是空的** —— 名单空 = 大屏永远拿不到"谁在线"，只能退回去猜。

**修法**：按真实结构解析（先把换行/空格压掉 → 取 `users` 数组 → 拆逗号 → 去引号 →
去掉 `user>>>` / `user_` 前缀和 `>>>online` 后缀）。

### 根因 ②：手机维护的"最后在线时刻"文件是**残缺**的

修复 ① 之后，脚本会把"在线名单里的人 = 现在"写进一份时刻文件。
但这份文件**曾经被人工清空过**，清空之后就只剩最近上线的 2 个人，
其余 5 个人**没有任何权威时间**。

**修法**：每次刷新时，从另一份由脚本为**全部用户**持久维护的活跃时刻文件回灌，
并且合并时**只取较大值**（只增不减，杜绝时间倒退）。

### 根因 ③（最关键）：Worker 用"本机房字节增长"当在线判据

边端（Worker）判断在线时，用的是"这个用户的流量计数比上一轮大了没"。
问题是 —— **这个比较是每个机房各自做的**，跨机房的计数天然不同：

| 机房 | 自己的上一轮计数 | 本轮计数 | 判定 |
|---|---|---|---|
| 甲 | 100 MB | 100 MB | 离线 |
| 乙 | 99 MB（少同步了一点） | 100 MB | **"涨了" → 在线** |

于是同一个用户，在甲机房是"离线"，在乙机房是"在线"，刷新一次就翻脸。
这也是"没人在线却显示一堆在线"的直接成因。

**修法**：改成三级判据，逐级降级，且**只用手机下发的权威数据**：

1. 在线名单**新鲜**（≤ 60 秒）→ 只认名单：在就是在线，不在就是离线，**绝不猜**；
2. 名单不新鲜 → 问「**在这份数据产生的那个时刻，这个人在线吗？**」
 判据 = 手机下发的该用户最后在线时刻 与 **这份数据自己的时间戳** 比对。
 这个算式**只用到数据里的两个数，不含本机房任何观察**，所以任何机房读同一份数据必然给出**同一个答案**；
3. 连最后在线时刻都没有（冷启动/旧版脚本）→ 才退回字节增长兜底。

### 派生问题 ④：两处"回退保护"把好数据盖成了坏数据

**4a. 时刻表**：新值与历史值合并时取 `max`。
历史里残留着旧版本各机房**自己推算出来的、偏大的脏时间戳**，
取 max 等于让脏值**永远压住手机的真值** —— 这是"越修越乱"的关键。
→ 改为：**只要本轮拿到手机数据，就整表重建**，不再与历史比大小；
交接时的兜底顺序改为「手机权威时刻表 → 手机每人最后活跃 → 旧机房推算值（最后手段）」。

**4b. 累计流量**：为了防止流量数字倒退，原来会把**整个旧对象**盖回来，
连带把旧的**在线状态 / 最后活跃 / 速率**一起盖了回去。
后果：本轮手机明明报"某人在线"，因为旧对象的累计值更大，就被旧对象覆盖成"离线"，
大屏把**正在线上的人显示成「刚断开」**。
→ 改为：**只回退必须单调不减的三个流量数字**，在线状态/最后活跃/速率一律保留本轮最新值。

### 派生问题 ⑤：前端两处口径不同源

| 位置 | 原来的判据 | 后果 |
|---|---|---|
| 用户连接状态板块 | 服务端权威状态 | 正确 |
| 用户管理表状态列 | `在线 或 本机房字节在涨` | 离线用户全显示「🟢 在线待命」 |
| 卡片右下角时刻 | `max(本机房增长时刻, 历史活跃)` | 与卡片自己的"几分钟前"打架 |
| 管理页首屏（服务端渲染） | 本机房字节在涨 | 首屏全绿 → 轮询一变全红（闪跳） |

**修法**：四处统一为同一套判据（服务端权威状态），并区分文案：
名单实时 → 「**此刻有连接**」；名单稍旧 → 「**手机端确认在线**」（不替数据打包票）。

## 3. 改了哪些文件

| 文件 | 改动 |
|---|---|
| 边端 Worker | 时刻表整表重建；三级在线判据；回退保护只回退流量数字；`最后活跃` 与 `connAt` 同源；管理表/首屏口径统一；卡片文案区分 |
| 节点脚本（报告类） | 时刻文件从全员活跃表回灌、只增不减 |
| 导出脚本 | 清理 13 条**早已过期**的替换规则（见第 6 节） |

> 节点脚本改动**不需要重启任何服务**：脚本是每轮被重新执行的，改文件即刻生效，用户无感。

## 4. 怎么验证（可复现）

**目的**：证明"同一个用户，在任何机房看到的数字都一样"。

1. 连续请求数据接口 N 次（每次间隔 200 ms），**记录每次响应头里的机房代码**；
2. 对每个用户，把 N 次结果里的「状态」与「最后在线时刻」分别去重；
3. **期望**：离线/从未连接的用户 —— 去重后**只有 1 个值**；真在线的用户 —— 每次都显示在线。

实测结果（连续 16 次、命中 6 个不同机房）：

```
用户A      状态=long        时刻变体=1
用户B      状态=online      时刻变体=10   ← 在线用户，时刻=“现在”，每秒都不同是正常的
用户C      状态=long        时刻变体=1
用户D      状态=long        时刻变体=1
用户E      状态=never       时刻变体=1
用户F      状态=long        时刻变体=1
```

修复前同一份测试会得到 4~5 个不同变体，且离线用户状态在 `long / online` 之间来回跳。

大屏实测：`在线 2 / 刚断开 0 / 近期活跃 0 / 长期离线 5 / 从未连接 1`，
8 个人的时间**各不相同**、且与每个用户的真实活跃历史对得上。

## 6. 顺带修掉的工具坑（会导致同步直接失败）

脱敏导出脚本里有一批"逐条点名替换"的规则，**命不中就报错退出**（这是故意的：
宁可报错也不要静默漏改）。其中 13 条针对的是**早已被重写的旧分组名/旧节点名**，
在源码里已经不存在 → 导出必然中断。

处置：逐条核对源码确认"确实没有对应文字可漏"之后**整块删除**，
而不是改成"宽容跳过" —— 保留"命不中即报错"的严格语义。

导出后校验：真实凭据残留 **0 处**（域名/密码/密钥/令牌/设备标识全部占位化）。

## 7. 给下一位维护者的三条纪律

1. **任何一个"给人看的时间/状态"，都必须能回答"这个数字是谁在什么时刻测的"。**
 各机房各自推算的数字，天生不可能一致 —— 这就是本报告全部问题的源头。
2. **跨机房要一致，判据里就不能含"本机房的观察"。**
 正确做法是把权威值（这里是节点脚本下发的时刻表）**随数据一起同步**，
 让所有机房**读同一份输入、算同一个式子**。
3. **"回退保护/取最大值"这类看起来更安全的写法，是这类 bug 的高发区。**
 单调不减的量（累计流量）才适合取 max；**状态类字段取 max 等于让脏数据永生**，
 只能"以最新的权威源为准"。本报告第 4a、4b 两条都是踩在这里。
