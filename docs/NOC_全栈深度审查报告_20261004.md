# NOC 全栈深度审查报告（2026-10-04）

> 审查方式：3 个并行审查代理（Worker/Cloudflare 后端、手机 adb+Termux、大屏前端）+ 主会话对手机、Termux、线上接口的现场复核。
> 范围：`worker_deploy.js`（6634 行）、`cf_deploy.py`、手机 6 个运行脚本、`/data/local/tmp` 现场、Termux、线上 `/api/*` 与 `/admin` 页面。
> 每条问题都给出 **方案 A/B/C**，⭐ 为推荐。选择方式见文末。

# 主题 1：数据真实性（用户红线，最高优先）

### T1.1 大屏静态 HTML 仍残留旧假值 [高]
- 证据：`worker_deploy.js:5108-5110`（`totalBytes=6.95 GB`、`downBytes=6.82 GB`、`upBytes=130.22 MB`）、`:5046`（`19 个活跃会话`）、`:5215`（`5 大分流通道全部 ONLINE`）、`:4834`/`:4914`（静态"刚刚/刚刚数据"）、`:4776`（水位初始 15%）、非高亮卡无条件"极优"徽章（:6507-6508）
- 影响：接口失败/首屏加载时，这些数字长期显示，用户无法分辨真假，违反"不允许假数据"红线。
- 方案A ⭐：全部改为 `--`/中性文案（"等待数据"），与已修的硬件卡一致。
- 方案B：首屏用"最后已知真实值"（存 localStorage）填充并加"缓存"标记。
- 方案C：不动（仅首屏可见，刷新后消失）。

### T1.2 手机端 pingTimes 假时间兜底残留（与 2026-10-04 修复自相矛盾）[高]
- 证据：`ping_scheduler.sh:155-160`——`T_KL<=0` 时回填 `NOW-50/-40/-30/-20/-10/NOW`
- 影响：`last_ping_times.txt` 被清空或某区永久失败时，六区被伪装成"10~50 秒前刚测过"且永远保留，大屏把"从未测到"显示成"N 分钟前"。
- 方案A ⭐：删除 155-160 六行兜底，T=0 如实上报（前端已有红色"未测到"渲染）。
- 方案B：保留兜底但加 `"unmeasured":true` 字段由前端渲染为"未测到"（要改 Worker+前端）。
- 方案C：不动。

### T1.3 兜底读错文件名 + 手机残留测试假数据 [高]
- 证据：`phone_report_traffic.sh:124` 读 `/data/local/tmp/last_times.txt`，但 `ping_scheduler.sh:17` 与 `fast_scan.sh:18` 写的都是 `last_ping_times.txt`。手机实测两个文件并存，`last_times.txt` 是我 2026-10-04 测试遗留的 20 秒等差假值。
- 影响：ping_cache 缺失/截断瞬间，上报会把测试残留假时间当真实 pingTimes 上屏。
- 方案A ⭐：`phone_report_traffic.sh:124` 改为 `last_ping_times.txt`，并删除手机上的 `last_times.txt` 残留。
- 方案B：反向统一（scheduler/fast_scan 改写 `last_times.txt`）。
- 方案C：fallback 时 pingTimes 全 0 不发旧值（可叠加 A）。

### T1.4 冷启动时间戳兜底把"没数据"伪装成"刚刚" [中]
- 证据：`worker_deploy.js:4081-4082`（`timestamp: serverNow, serverTime: serverNow` 的初始 payload）；`:4108` `updatedAt = s.updatedAt || '刚刚'`
- 影响：无快照时年龄恒 0、"刚刚数据"绿色——与红色"未测到"语义矛盾。
- 方案A ⭐：初始 payload 的 timestamp 设 0，前端按"未测到"渲染。
- 方案B：初始 payload 加 `noData:true` 标记，前端整体显示"等待手机接入"。
- 方案C：不动。

### T1.5 `DEFAULT_USERS` 预置 `lastSeen:'刚刚'`、`lastActive: Date.now()` [低]
- 证据：`worker_deploy.js:3202-3208`
- 影响：新用户从未上线也显示"刚刚"，属于软性编造。
- 方案A ⭐：改为 `'从未'` 与 0。
- 方案B：前端对无真实 lastSeen 数据时显示 `--`。
- 方案C：不动。

### T1.6 充电时无条件显示"恒温健康" [低]
- 证据：`worker_deploy.js:6231`
- 影响：无温度数据/高温时仍断言"恒温健康"。
- 方案A ⭐：有 temp 数据且 <45°C 才显示"恒温健康"，否则 `--`。
- 方案B：直接删掉该副标题。
- 方案C：不动。

# 主题 2：安全与凭证

### T2.1 `/cf` 公开端点泄露可用订阅（含用户B 真实 UUID）[高]
- 证据：`worker_deploy.js:3656-3664`（`/cf` 无任何鉴权返回 CF_TEST_YAML）；`:20-2500` 区间 YAML 内嵌 `uuid: ${VLESS_UUID}` 180+ 处；`shared_legacy` 万能 UUID `27b6d19b-...`（:2911）同样硬编码且手机端必然放行
- 影响：任何人访问 `https://${WORKER_HOST}/cf` 即拿到"节点清单+真实 UUID"的可用订阅，等于免费机场。
- 方案A ⭐：`/cf` 移除公开路由，改为需 `?pwd=`（或直接删除该端点，测试配置走内部渠道）。
- 方案B：`/cf` 保留但 UUID 换成占位符（下载者自己填）。
- 方案C：轮换所有用户 UUID 并定期轮换（工程量大，历史订阅全失效）。

### T2.2 仓库明文凭证 [高]
- 证据：`.cf_token`（CF API Token）、`tunnel_creds.json`（TunnelSecret）、`SESSION_TRANSCRIPT.jsonl`×2（约 10MB+8.7MB，含 664 处密钥字符串）、`config*.json`、`test_*.json`
- 影响：仓库/备份一旦外泄，全部凭证裸奔。
- 方案A ⭐：把这些文件移出项目目录（如移到 `C:\NOC_secrets\`），仓库内只留 `.gitignore` 清单；转录文件删除或加密归档。
- 方案B：保留位置但轮换全部密钥（CF Token、Tunnel Secret、SYNC_SECRET、UUID）。
- 方案C：不动。

### T2.3 `/sub` 对任意 ≥6 字符 token 发放订阅 [中]
- 证据：`worker_deploy.js:4337-4352`（未知 token 生成"临时用户"并照发完整节点列表）
- 影响：未授权者能拿到节点列表（其 UUID 不在手机放行名单，实际连不通，但信息泄露+给人"有戏"的错觉）；未来若手机配置改为放行任意 UUID，立即变成免费使用。
- 方案A ⭐：未知 token 一律 403"订阅不存在或已被禁用"。
- 方案B：未知 token 只返回 notice 占位配置，不给真实节点。
- 方案C：保持现状（容灾宽松），但在大屏显著记录"未登记拉取"次数。

### T2.4 存储型 XSS：用户名/域名未经转义进 innerHTML 与服务端模板 [中]
- 证据：`worker_deploy.js:5592/5655/5618`（`u.name`、`item.domain` 进 innerHTML）；`:4584/4595`（`${u.name}`/`${u.token}` 属性逃逸）
- 影响：管理员若添加名为 `<img onerror=...>` 的用户，任何打开大屏的人中招。
- 方案A ⭐：所有插值统一走 `escapeHtml()` 转义函数；token 本身白名单 `[a-zA-Z0-9_-]`。
- 方案B：改用 textContent/DOM API 渲染。
- 方案C：在 add 表单入口做字符白名单（治标）。

### T2.5 密码在 URL query string 中 [低]
- 证据：`/admin?pwd=`、`/api/stats_data?pwd=`、`/api/live?pwd=` 全部用查询参数
- 影响：密码进浏览器历史/日志/Referer；Worker 访问日志可见。
- 方案A ⭐：改 Cookie/Authorization 头鉴权（改动前端+Worker，中等工作量）。
- 方案B：保留 query 形式，但定期轮换 ADMIN_PASSWORD（成本最低）。
- 方案C：不动。

# 主题 3：进程生命周期与容灾（手机侧）

### T3.1 run_daemon.sh 更新脚本后旧进程继续跑旧代码 [高]
- 证据：`run_daemon.sh:2-5` 只杀 xray/cloudflared/traffic_daemon，不杀 ping_scheduler/node_probe；daemon 保活靠 `pgrep`（:75-77），旧 scheduler 活着就永远不被替换
- 影响：任何脚本修复都到达不了运行中的旧进程——旧 bug/旧假数据回魂的总根源（我 2026-10-04 部署时就手动杀过一次，但 `run_daemon.sh` 本身没修）。
- 方案A ⭐：`run_daemon.sh` 增补 `pkill -f ping_scheduler.sh/node_probe.sh/fast_scan.sh/report_traffic.sh`（照 `clean_restart2.sh` 的清单），一次根治。
- 方案B：各脚本启动时自校验 md5，与 `.versions` 不符即自杀交给看门狗换血。
- 方案C：靠运维纪律每次手动 `clean_restart2.sh`。

### T3.2 手机重启后整套系统不自动恢复 [高]
- 证据：无 magisk、无 init.d、无 termux-boot、`/data/adb` 不存在；Termux 已装但家目录为空
- 影响：一次重启 = NOC 全站静默停摆，且手机侧无自愈、无告警。
- 方案A ⭐：装 Termux:Boot（F-Droid 版），把 `start_vpn.sh` 放进 `~/.termux/boot/`，开机自动拉起（手机已解锁 bootloader，改动最小）。
- 方案B：刷 Magisk 用 `/data/adb/service.d/` 自启（更稳，但动系统）。
- 方案C：不做自启，改为"PC 端存活监控 + 断流告警 + 人工重连"SOP。

### T3.3 daemon 单点 + 8 秒超时腰斩配置同步 + 孤儿 curl [高]
- 证据：`traffic_daemon.sh:82`（`timeout -k 1 8`）；同步链路最坏 3s(POST)+5s(users GET)+5s(users push)+5s(config)+1s(test)≈19s > 8s；toybox timeout 只杀直接子 sh，其下 curl 变孤儿继续跑
- 影响：Worker 慢时同步必被腰斩 → force_sync 永不完成 → 与 T5.1 叠加形成每 6s 重推风暴；被杀轮的 curl 仍完成 POST 造成重复上报；daemon 死了全链无自愈。
- 方案A ⭐：硬超时放宽到 15s；配置同步改为循环外后台任务（上报 ≤6s 完成，同步结果下轮生效）。
- 方案B：同步阶段 curl 全部 `--max-time 3` 压进 8s（牺牲同步成功率）。
- 方案C：daemon 用 `setsid` 起子进程，超时杀整个进程组。

### T3.4 手机日志无限增长 + cf 截断式轮转与持有 fd 冲突 [中]
- 证据：`report_traffic.sh:75-83` 只轮转 cf_named.log（5MB 截断），`xray_live.log` 无轮转（实测 ≈5MB/天）；截断 `: > file` 后 cloudflared 旧 fd 继续从旧偏移写 → 文件头 NUL 空洞 → stat 恒 >5MB → 每 6s 轮转一次 + cfErrors 指标失真
- 影响：磁盘数月后 GB 级；cfErrors 指标被空洞污染。
- 方案A ⭐：轮转改为「pkill cloudflared → mv 旧日志 → 看门狗自动拉起」；xray 同理按阈值（如 50MB）在低峰时段重启+mv。
- 方案B：日志只压级别（xray 已是 warning），接受增长、每月人工清。
- 方案C：不动。

### T3.5 Termux 旧脚本残留（含假数据版）[中]
- 证据：`/data/local/tmp/tunnel_staging/shortcuts/`（start.sh/stop.sh/status.sh）、`termux_report_traffic.sh:32-45/58` 仍为编造值；`start_all.sh` 指向 `$HOME/xray`
- 影响：当前无第二套在跑（已实测），但有人打开 Termux 手滑跑了 start.sh 就产生第二套上报+假数据回灌。
- 方案A ⭐：删除 `tunnel_staging` 与手机端所有 `termux_*` 残留，卸载 com.termux（或至少删其 home 下脚本）。
- 方案B：保留 Termux（装 Termux:Boot 用，见 T3.2），但清空旧脚本。
- 方案C：不动。

### T3.6 `/data/local/tmp` 残留 165 个文件（约 100MB）[低]
- 证据：`report_traffic.sh.bak_*`×8、`ping_scheduler.sh.bak_*`×10、`traffic_daemon.sh.bak_*`×2、`_diag/_bench/_nr/_ns` 等 20+、`tunnel_staging`（含 70MB 二进制）、`ps.txt/ps2.txt` 等
- 影响：全部可执行，误跑旧 `.bak` 即双重上报/假数据回灌；占 100MB。
- 方案A ⭐：保留最新 6 脚本+config+必需数据文件，其余 rm（清理前先核对引用）。
- 方案B：移到 `/sdcard/NOC_archive` 归档。
- 方案C：不动。

# 主题 4：Worker 缓存一致性

### T4.1 stats_latest 双 put，max-age=86400 覆盖 300 [高]
- 证据：`worker_deploy.js:3889-3897`（max-age=300）随后 `:3900-3913`（max-age=86400）覆盖
- 影响：同机房陈旧快照上限从 5 分钟放大到 24 小时——这与你"5 分钟内才接受"的判据直接冲突（跨机房问题因此被放大）。
- 方案A ⭐：删掉第二次 put（重复且有害），保留 300。
- 方案B：保留一次 put 但 max-age 设 30s。
- 方案C：不动。

### T4.2 users_changedAt 缓存 30 天 + 内存无 TTL → 徽标冻结 [中]
- 证据：`worker_deploy.js:3414`（内存无 TTL）、`:3533`（Cache 30 天）
- 影响：跨机房读变更时刻可能长期读旧值，"用户库已变更"徽标失灵。
- 方案A ⭐：Cache TTL 改 60s；内存加 60s TTL。
- 方案B：changedAt 改存 KV 键 `noc:users:changedAt` 并 cacheTtl 60。
- 方案C：不动。

### T4.3 域名统计累加器跨 isolate 丢失/不一致 [中]
- 证据：`worker_deploy.js:3200/3786-3787`（`userDomainAccumulators` 只在 isolate 内存累加，从不独立持久化；快照只含最后写入 isolate 的视图）
- 影响：域名偏好统计随 isolate 冷启动清零、随请求落点跳变。
- 方案A ⭐：累加结果随 stats_latest 快照写入 Cache 并在冷启动时恢复（像 userTraffics 一样）。
- 方案B：域名统计改为"手机每次报全量窗口值，Worker 只取最新"（不累加）。
- 方案C：删掉该功能。

### T4.5 删除 7 人默认成员完全无效（永久合并基底）[高]
- 证据：`worker_deploy.js:3453/3467/3478/3501/4015` 五处 `{ ...DEFAULT_USERS, ...parsed }` 永久合并；`getUserStoreVersion`（:2898）基于合并后视图 → 删除默认用户的版本哈希不变 → 手机永不感知；且手机下一次回推（`phone_report_traffic.sh:632-643`）会把被删用户重新写回 KV
- 影响：在后台删掉"用户A/用户C"等默认成员，`/sub` 照发订阅、手机 xray 仍放行其 UUID、刷新后还复活——"禁用/删除"功能对 7 人默认名单形同虚设。
- 方案A ⭐：默认名单只作为"首次初始化种子"，一旦 KV 有值就以 KV 为唯一真相（不合并）；删除即真删除。
- 方案B：保留默认名单但引入 `deletedTokens` 墓碑列表参与版本哈希（默认用户可删但名单兜底仍在）。
- 方案C：不动（默认 7 人视为"不可删"并明确告知）。

### T4.4 syncReqMemory 兜底可复活已消费指令 [中]
- 证据：`worker_deploy.js:3815`（`readSyncRequest(env) || syncReqMemory`）
- 影响：点刷新落在 isolate A、手机确认落在 isolate B 清 KV 与自己的内存后，A 内存里旧指令复活 → 已消费指令被再次下发（有 ackedId 守卫部分缓解，但写 KV 的旧请求仍可能回来）。
- 方案A ⭐：报告路径只信 KV（`readSyncRequest`），彻底移除 `|| syncReqMemory`；syncReqMemory 仅留给后台页即时显示。
- 方案B：保留内存兜底但每次下发前校验 ackedId（前端已做，服务端补上）。
- 方案C：不动。

# 主题 5：KV 配额与请求频率

### T5.1 每次上报 2 次无 TTL KV 读（sync:req + scan:req）[中]
- 证据：`worker_deploy.js:3815`（sync:req）、`:3923`（scan:req），均无 cacheTtl；约 14,400 上报/天 → ≈29,000 读/天（实测全天 11,788 含其它路径，仍安全但吃 30% 额度）
- 影响：离 100k 上限有距离，但这是最大的单一读源；未来用户量/频率上升先爆这里。
- 方案A ⭐：两键合并为单键 `noc:cmd`（`{type:'scan'|'sync', id, at}`），每次上报只读 1 次。
- 方案B：scan:req 保留 0 TTL（手动刷新要快），sync:req 加 cacheTtl 30。
- 方案C：不动。

### T5.2 用户库推送触发条件过宽 + 失败重试风暴 [中]
- 证据：`phone_report_traffic.sh:607`（`REMOTE_VER != LOCAL_VER || force_sync` 都触发 push）、`:645-663`（new_config 下载/xray -test 失败时不写 VER_FILE → 版本差永久存在 → 每 6s 重推 users_push）
- 影响：点一次"手动刷新"即触发一次全量 push（即使无成员变更，与"仅成员变更时写"注释矛盾）；与 T3.3 叠加可成 KV/HTTP 重试风暴。
- 方案A ⭐：拆分条件——版本不等才 push；force_sync 只拉不推。
- 方案B：push 前先 GET 比对，相同跳过。
- 方案C：push 失败退避 10 分钟（防风暴，成员变更延迟）。

# 主题 6：手机数据链正确性

### T6.1 traffic_daemon.sh 的 sub_ms 仍是 32 位溢出 [中]
- 证据：`traffic_daemon.sh:42` `F=$(date +%s%N | tail -c 10)` 取的是"1 位秒+9 位纳秒"，F 最大 9.99e9 > 2^31；手机实测溢出 → `report=` 记录约 70% 概率是错的（不影响 NAP 调步，但日志不可信）
- 方案A ⭐：`tail -c 9` 只取 9 位纳秒再 /1e6（0-999，永安全）。
- 方案B：用 awk 做除法绕开 sh 算术。
- 方案C：放弃毫秒全用整数秒统计。

### T6.2 ping_cache / last_* 无锁并发写 + 读写竞态 [中]
- 证据：`ping_scheduler.sh:100-106/268-274` 与 `fast_scan.sh:65-71` 都 `echo > 文件` 直写同一组 5 文件，无锁；`report_traffic.sh:9` 定义 `LOCK_PING` 但从未使用
- 影响：手动刷新时 scheduler 与 fast_scan 交错写：新值被旧值覆盖、六区数据混搭；report 读的瞬间若遇 `> file` 截断读到空文件 → 触发 T1.3 兜底。
- 方案A ⭐：所有落盘统一"写 .tmp + mv"原子替换（约 10 行改动）。
- 方案B：mkdir 目录锁互斥三个写者。
