Field Manual · 从零到可运维

一台手机当出口 · 完整搭建与运维教程

核心只有一句话：一台手机，就可以当作出口。手机装两个程序——一个接住流量、一个把回程隧道打通；你在终端上的代理软件里填好配置、连上它，流量就从这台手机所在的网络出去。不需要服务器，不需要公网 IP，不需要端口映射。全文分客户端与手机端两侧，每一步都说明要做什么和这一步到底在解决什么问题。

客户端：订阅 · 导入 · 优选 手机端：接住流量 · 隧道回程 · 自动保活 文中所有 IP / 域名 / 密钥均为占位示例
阅读方式：只想把客户端跑起来 → 直接看 第 5 章（用户端）； 要自己搭一套 → 按 第 3 章（服务端） 顺序做； 已经在跑但总出问题 → 看 第 10 章（排错） 和 第 9 章（数据流）。

01这套系统到底是什么

先用一句话说清楚它的价值，后面所有设计取舍都是从这句话推导出来的。

它把一台放在海外家里的手机，变成一条可以被远端客户端使用的、出口 IP 属于当地住宅宽带的网络通道。

为什么这件事有价值？因为互联网上大量服务会对「来源 IP 的类型」区别对待：机房 IP（云服务器）容易被风控、被限流、被判定为数据中心流量；而住宅宽带 IP 在各类风控模型里天然更"干净"。传统的机房代理做不到这一点，因为它的出口就是数据中心。

所以整套系统的技术目标非常明确：让客户端的流量，最终从一个真实的家庭宽带的公网 IP 出去。围绕这个目标，才衍生出后面所有的设计：

目标由此产生的要求
出口必须是住宅 IP不能买云服务器做出入口，必须有一台真实接入家庭宽带的设备常驻运行
设备在别人家里，无人值守必须能自愈、能远程诊断、能远程重启，不能靠"去现场重启一下"
客户端在国内，直连海外会被干扰必须借一层全球任播网络（Cloudflare）做前置，并把流量伪装成正常的 HTTPS 访问
家庭上行带宽有限、要省电所有探测/心跳频率必须精打细算，能合并的上报必须合并
运维要能看见"此刻到底通不通"必须有一块能实时反映链路每个环节的监控面板
数据不能造假测不到就显示"未测到"，宁可留空也不填数字
本教程的边界：只讲用户端（拿订阅、导入、连通、调优）和服务端（边缘 Worker、住宅节点、采集脚本、监控大屏）。 把它当作一条工程链路来拆解——每一层的职责、参数的含义、失败时怎么判断。

02整体架构与数据全景

两个方向的数据流，是理解这套系统的钥匙：一条是"用户的流量"，一条是"监控的遥测"。

两条流的分工

① 用户流量（客户端 → 公网）

  • 客户端把流量封装成看起来像访问某个域名的 HTTPS
  • Cloudflare 任播把请求落到离客户端最近的边缘机房
  • 边缘通过已建立的反向隧道把流量送回住宅节点
  • 住宅节点的代理核心解密后，用家庭宽带的公网 IP 访问目标

② 监控遥测（节点 → 大屏）

  • 节点上的采集脚本周期性测量各环节的时延、丢包、落点
  • 每轮把结果合并成一个包主动上报给边缘 Worker
  • Worker 把最新快照存在边缘内存/缓存里
  • 浏览器用长轮询取回，秒级刷新大屏
为什么遥测要"节点主动推"而不是"大屏去拉"？ 因为住宅节点在 NAT 后面，没有公网入口，外部无法主动连它；而它主动出去的连接是通的。整条链路能成立，靠的就是这个方向性——所有的"远程控制"都必须搭在"节点主动上报"这趟车上（见 第 10 章 指令通道）。

角色与职责速查

角色它负责什么它不负责什么挂了会怎样
用户端客户端
用户侧		 把本机流量封装、按规则分流、发送到优选 IP 不做任何测量与上报 只有这一个用户断，其他人不受影响
Cloudflare 边缘
服务端		 就近接入、伪装成正常站点、Worker 计算、隧道中转 不存储用户的浏览内容 大面积不可用（系统级故障）
住宅节点

监控大屏

03服务端 · 六步搭建

从一台能上网的设备，到一条可运维的出口链路，总共六步。每一步都先讲"做什么"，再讲"为什么必须这样"。

步骤 ① 准备住宅节点

  1. 选一台长期通电、接入家庭宽带的设备（旧手机 / 迷你主机 / 软路由都行），确认它的公网出口就是家庭宽带 IP。 为什么：出口 IP 的归属由这一台设备决定，选错设备后面全白做。可以用一条命令验证：curl -s https://www.cloudflare.com/cdn-cgi/trace 看返回里的 loc 与 ip 字段，确认地理位置与运营商归属符合预期。
  2. 把它固定在内网的一个地址上（路由器的 DHCP 静态绑定），并确认内网地址不会因为重连而变。 为什么：所有采集脚本、隧道配置、远程诊断命令都写死了内网地址；地址一变，隧道断开、脚本失联，而你人不在现场。
  3. 关掉会"杀掉后台进程"的系统策略：省电模式、后台限制、自动清理内存。 为什么：这套东西要靠常驻进程活着。系统一睡，隧道就断——表现就是"所有人同时上不了网，大屏数据也冻结"。这是住宅节点方案最高频的故障源。
  4. 准备一个可以远程操作它的通道（同网段的跳板机 / 局域网的 SSH / 调试桥）。 为什么：节点在别人家里。没有远程通道，任何"改一个参数"都要变成"上门一次"。

步骤 ② 在节点上安装代理核心

代理核心是这条链路的"发动机"，它同时要做两件事：接住从隧道进来的流量，和把流量从家庭宽带发出去。

配置块作用要点
inbounds 入站接收隧道送来的流量监听本机端口，协议与客户端一致；按路径拆分成多个入口（见第 4 章）
outbounds 出站把流量发往目标默认 freedom 直连——这一条决定了"出口是住宅 IP"
stats / api 统计让采集脚本能读到实时流量开一个只监听 127.0.0.1 的统计端口；绝不能暴露到公网
log 日志审计与排错必须开访问日志——流量统计与访问域名统计都是从日志里解析出来的
两个必须守住的纪律： ① 统计接口只绑 127.0.0.1，对外一律不开；② 日志要轮转，否则长时间运行会把磁盘写满——磁盘一满，隧道与代理会一起挂。

步骤 ③ 建立隧道（让流量能"回到"节点）

  1. 在 Cloudflare 侧创建一个命名隧道，拿到一串隧道凭据。 为什么：家庭宽带没有公网入口（运营商 NAT），也没法做端口映射。反向隧道让节点主动连出去、由 Cloudflare 记住这条连接，外部流量就能顺着这条已建立的连接回来——不需要任何入站端口。
  2. 用凭据在节点上启动隧道客户端，并把它配成常驻服务。 为什么：隧道是唯一的"回程路"。它断了，用户的代理就全部超时（而监控上报也会一起断，大屏会显示"数据冻结"）。
  3. 把隧道的入站指向代理核心监听的那个本地端口。 为什么：隧道只负责"搬运"，不认识代理协议。真正的鉴权与伪装由代理核心完成——两层各管一段，任何一层换实现都不影响另一层。
  4. 顺带拿到一个"看起来很正常"的域名与自动证书。 为什么：客户端与边缘之间必须是标准 HTTPS：真实域名、有效证书、正常 TLS 指纹。这才是"伪装成正常访问"的基础。

步骤 ④ 部署边缘 Worker

Worker 是这套系统的"前台+控制面"：用户的流量不经过它转发，但订阅分发、遥测聚合、监控页面全在它上面。

路由方向职责关键设计
/sub?token=…用户端 ← 服务端按 token 下发节点配置（Clash / v2ray 两种格式）未知 token 发临时配置但不入库；展示字段只写缓存不写持久层
/api/report_traffic节点 → 服务端接收节点每轮上报的遥测校验共享密钥；合并策略为逐字段按各自时效合并；响应里回带指令
/api/live大屏 ← 服务端长轮询：有新数据立刻返回比 SSE 兼容性更好；失败重试指数退避，防止打爆配额
/api/stats_data大屏 ← 服务端全量快照（用户表、流量、历史波形…）缓存优先；载荷做减法，避免边缘处理耗时虚高
/api/manual_scan大屏 → 节点下发"立刻全速扫描一次"的指令只允许 POST；写入单键指令，节点确认后才删除
/admin浏览器监控大屏页面本体自包含单页；版本号不一致时自动刷新
/chart.js浏览器图表库本地直出内嵌，避免第三方 CDN 抖动影响首屏
部署纪律（这几条是一次次踩坑换来的）： ① 部署输出绝对不能截断看——曾因只看最后一行，把报错当成成功很久； ② 部署后至少等 20~30 秒再验证线上版本； ③ 判断"是否生效"要比对三处版本号：源码里的、接口返回的、页面内嵌的，三者一致才算成功。

步骤 ⑤ 在节点上部署采集脚本

节点要跑的不止代理核心，还有一套"值班系统"。它的五个成员各有分工（详细原理见 第 8 章）：

脚本角色节奏没了会怎样
traffic_daemon看门狗 + 节拍器常驻循环没有人保活其它进程，整个值班系统逐步死光
report_traffic汇报员：组装并上报遥测约 6 秒大屏全部数字变成"未测到"
ping_scheduler区域测绘员：测各接入点时延/丢包60 秒一轮时延矩阵空白，质量评分无数据
edge_probe边缘探针：测到边缘的单次往返15 秒时延分布/端到端之和无数据
node_probe节点巡检员：逐个探中转节点10 秒 1 个节点矩阵永远停在"待探测"
三个必须遵守的部署规则： ① 改完脚本必须重启进程——脚本是启动时读入内存的，改文件不重启等于没改； ② 行尾必须是 LF——CRLF 会让 shell 报语法错误； ③ 重启顺序不能错：先杀看门狗（否则它会不断把子进程复活），再杀其余，最后只拉起一个看门狗。

步骤 ⑥ 维护用户库（谁能用这条链路）

  1. 给每个使用者分配一个独立的身份令牌，由令牌派生出属于他的连接标识。 为什么：一人一令牌才能做到"停用某个人"而不影响其他人，也才能区分流量归属。令牌与派生标识都不要复用、不要外传。
  2. 把用户库做成有唯一权威源的数据，其余位置都只是加速缓存。 为什么：边缘网络是分布式的，"内存里的列表"在不同机房是不同副本。曾经出现过同一份名单在两个入口显示不同人数、甚至同一个人重复两行——根因就是"没有权威源"（详见 第 10 章）。
  3. 把"写"限制在极少的几个动作上：新增、停用、删除、节点回推。日常的每一次"打开页面""拉订阅"都不应该产生写操作。 为什么：免费额度的写入配额是按天算的，而读取和上报是高频的。把高频路径上的写全部去掉，是这套系统能长期稳定运行的根基（见 附录·设计约束）。
  4. 保留一个"强制同步"的手动入口，用于主人库与边缘不一致时人工对齐。 为什么：自动化总有对不上的时候（网络抖动、指令丢失）。有一个可手动触发、可确认结果的通道，排障成本会低一个数量级。

04协议与参数：为什么必须是这一套

这一章解释"为什么参数写成这样"，因为用户端导入失败、连不通，九成问题都出在这几个字段上。

4.1 为什么是「TLS + 长连接伪装 + 标准端口」

选择解决什么问题代价
走 443 端口与正常 HTTPS 不可区分，任何网络环境下都最不容易被单独限制与真实网站共享端口，必须靠域名区分
真实域名 + 有效证书握手阶段完全合法，不触发证书告警需要一个域名并保持解析正确
HTTP 传输层伪装（把流量切成看似普通的 HTTP 请求/响应）流量形态与普通网页访问一致，比早期的长连接方案更难被识别配置项更多，参数必须与客户端完全一致
多路径分流（/kl、/hk…）同一条隧道上可以挂多个"入口路径"，便于按接入点区分与排障客户端每个路径对应一个配置条目

4.2 那个"必须带"的浏览器指纹参数

现场结论：客户端配置里如果缺了 client-fingerprint: chrome，表现是全部节点超时——不是变慢，是彻底连不上。

原因：Cloudflare 会对 TLS 握手的指纹做检查，非浏览器指纹（例如各种库自带的默认指纹）会被直接拦掉。客户端把指纹伪装成主流浏览器，握手才会被当作正常访问放行。

排查口诀："全部节点都超时"→ 先怀疑指纹参数缺失或写错；"个别节点超时"→ 去看那个节点的优选 IP 是否失效。

4.3 一条订阅里到底有什么

客户端拿到的订阅是一个"节点列表"，每一项的结构基本相同，差异只在接入地址与路径：

vless://<用户标识>@<接入地址>:443
      ?encryption=none
      &security=tls
      &sni=<伪装域名>
      &fp=chrome                 ← 浏览器指纹，缺了必超时
      &type=xhttp                ← 传输方式
      &host=<伪装域名>
      &path=%2F<路径>            ← 每项不同：/kl /hk /sg …
      &mode=auto
      #<显示名>                  ← 命名规则：地区-实测落点-序号

两种常见输出格式：Clash 系（YAML，给带图形界面的客户端）与 v2ray 系（一串 vless:// 链接的 Base64，给通用客户端）。两者内容等价，只是包装不同。

命名规则为什么重要：节点名里的"实测落点"不是猜的城市，而是探测时边缘真正返回的机房码。多个接入地址因为任播特性可能落到同一个机房——这时候按城市命名就是在骗人（名字是真的、位置是假的）。所以命名一定要以实测为准。

05用户端 · 五分钟接入

用户端只有四个动作：拿到订阅、导入、验证、调优。不需要理解服务端。

步骤 ① 拿到你的订阅链接

订阅链接通常长这样（下面全部是占位示例，真实值请以管理员给你的为准）：

https://<你的入口域名>/sub?token=<你的专属令牌>&type=clash
https://<你的入口域名>/sub?token=<你的专属令牌>&type=v2ray
参数含义注意
token你的身份令牌等同于账号密码，不要截图外发；泄露了就让管理员换一个
type输出格式clash 给图形客户端，v2ray 给通用客户端。选错了导入会失败，但可以随时改

步骤 ② 导入客户端

  1. 打开客户端的「订阅 / 配置」页面，新建一个订阅，把链接原样粘贴进去。 为什么原样：链接里的 & 和 ? 都是语法的一部分，手动"美化"一下就会解析失败。
  2. 点「更新 / 下载」，等它把节点列表拉下来。 这一步实际发生了什么：客户端发了一次普通 HTTPS 请求到边缘。边缘根据 token 找到你的身份，现场生成一份属于你的节点清单返回。所以"更新订阅"是一次鉴权动作，不是下载一个固定文件——管理员改了节点，你更新一下就能拿到最新的。
  3. 确认列表里出现了节点，命名形如 地区-落点-序号。 为什么看名字：名字里的落点是实测的，能帮你判断"哪个节点实际离出口最近"。
常见导入失败原因：① 用了 type=v2ray 的链接但客户端只吃 YAML（反过来也一样）； ② 链接被聊天软件自动加了奇怪的换行/空格；③ 令牌已被停用或输错了一个字符。

步骤 ③ 验证连通（最重要的一步）

  1. 连上任意一个节点，然后访问一个能显示出口信息的页面（例如常见的 trace 类接口）。 看什么：返回里的 ip 与 loc。如果 loc 是你预期的国家/地区，说明链路成立。
  2. 把这个 ip 拿去查一下归属类型。 为什么要查：这一步才是"验证产品价值"——确认出口是宽带/住宅而不是机房。如果显示为数据中心，说明流量没走预期出口。
  3. 如果全部节点都超时，先怀疑客户端指纹参数；如果只有个别节点超时，换一个节点。 判断依据："全挂"通常是配置层问题（见第 4 章 4.2），"个别挂"通常是那条路径的优选 IP 失效。

步骤 ④ 分流规则（让该走代理的走代理）

推荐做法

  • 只把需要的流量指向代理（规则模式）
  • 把国内常用服务直连，减少无谓绕行
  • 需要固定出口的场景单独建一条规则

为什么不要全局

  • 全局会把所有流量压到一条家庭宽带上
  • 家庭上行带宽有限，容易互相拖慢
  • 节点侧流量统计也会被无关流量淹没

06优选 IP：用户端唯一需要动手的调优

同一个域名，在不同网络下会被解析到不同的边缘机房；换一个接入地址，时延可能差一倍。

6.1 为什么需要"优选"

边缘网络是任播的：同一个域名在全球有很多接入点，网络会把你的请求送到"它认为最近"的那一个。但"它认为最近"和"实际最快"经常不一致——尤其在跨境场景下，路由策略、运营商互联质量都会让某个接入点明显更快或更慢。

所以客户端可以在订阅节点里内置一批候选接入地址，让用户测速后挑最快的用。这就是"优选 IP"的全部含义。

6.2 怎么做

  1. 用客户端的「测速 / 延迟测试」功能，对订阅里所有节点跑一遍。 注意：这里测的是"你的设备 → 接入地址"的第一跳，不代表整条链路的最终速度，但它是你能控制的那一段。
  2. 挑最快的 2~3 个，日常用第一个，卡的时候切第二个。 为什么要备选：接入点的质量会随时间波动（跨境线路尤其如此），一个备选能省掉大量现场排障。
  3. 换网络环境（换运营商、换城市、从 WiFi 切到移动数据）后重新测一次。 为什么："最近"是从你的网络出发算的。你的出发点变了，最优接入点也会变。
一个常见误区：把节点名里的"落点"当成"离我近"。落点是出口侧的边缘机房，跟你所在的位置无关。判断快慢永远以你自己的实测为准。

07服务端 · 节点矩阵与订阅分发

"节点"在这套系统里有两层含义：用户看到的接入点，和节点侧要逐个巡检的对象。

7.1 一张清单驱动三个地方

系统里有一份节点清单，它是唯一来源，同时驱动三件事：

消费方怎么用这份清单
订阅下发 /sub为每个节点生成一条客户端配置，节点名按"地区-实测落点-序号"生成
监控大屏的节点矩阵渲染成一格一格的卡片，显示实测时延与状态
节点侧巡检脚本随遥测响应下发到节点，落地成一份清单文件，巡检脚本按顺序逐个探
工程上的取舍：这份清单目前是写在边缘代码里的。好处是"改一处、三处同步"，绝不会出现"订阅里有、大屏上没有"的不一致；代价是增删节点必须改代码并重新部署。理解这一点能省下很多排障时间——当用户问"为什么新节点没出现"，答案通常是"还没部署"。

7.2 节点是怎么被巡检的

  1. 清单随每轮遥测响应下发到节点，节点把它写成一份本地文件。 为什么用"响应携带"这种方式：节点在 NAT 后面、外部连不进来，所以"配置下发"只能搭在"节点主动上报"的响应里。这也意味着下发有延迟（最长一个上报周期）。
  2. 巡检脚本按文件顺序，固定节奏（例如每 10 秒一个）逐个探测，并把"当前探到第几个"写出来。 为什么按顺序而不是并发：并发探测会在短时间内产生大量连接，对家庭宽带是明显冲击；顺序探测把负载摊平。而"当前索引"上报给大屏后，大屏才能把"测速中"的高亮严格框在正确的格子上——不按时间戳猜。
  3. 每轮把探测结果（可达性、时延、实测落点）随遥测一起上报。 为什么要带落点：中转节点也可能"名字写着 A 地、实际落在 B 地"。把实测落点显示出来，名字与事实不一致时一眼可见。
一个踩过的坑（值得记住）：巡检结果去重时如果用"保留第一条"的写法，第一轮填满全部节点后，后续的新结果会全部被丢弃。表现极其迷惑：文件修改时间一直在变，内容却冻结在几小时前——大屏上就是"所有节点都是两小时前的数据"。正确写法是保留最后一条。

7.3 跨机房一致性：为什么"内存里的名单"靠不住

边缘计算是分布式的：同一个服务在全球很多机房各跑一份，机房内部还可能同时存在多个实例。写在模块级变量里的数据，只在那个实例里有效。

层可见范围速度适合放什么
实例内存单个实例最快高频只读的派生结果
机房缓存同一机房所有实例快遥测快照、展示字段——跨实例但不必跨机房
全局键值存储全球较慢、有配额必须全球一致的权威数据（如用户库）

历史上出现过的"同一份用户名单在两个入口显示不同人数""某个人重复两行""删掉的用户还能拉到订阅"，根因都是把"应该全球一致"的数据放在了"只在一个机房有效"的层里。修法是把权威数据提到全局键值存储，内存与缓存降级为纯加速层。

08服务端 · 监控：五条采集链路

监控不是"顺便加的功能"，它决定了出问题时你花 5 分钟还是 5 小时定位。这里讲每条链路测什么、多久测一次、为什么是这个频率。

8.1 五条链路各自在回答什么问题

链路回答的问题频率为什么是这个频率
① 遥测上报 "节点本身还好吗"（电量、温度、充电、WiFi、在线时长、连接数、累计流量） 约 6 秒 这是整个监控体系的心跳。太快浪费家庭带宽与配额，太慢则"断开告警"会明显滞后。6 秒是"及时"和"省"的平衡点
② 区域时延/丢包 "我的流量从哪个接入点进去最快、稳不稳" 60 秒一轮 时延是慢变量，一分钟内的变化有限；而每个点要采多次才能抵抗抖动，频繁测没有收益只有开销
③ 边缘往返 RTT "节点到边缘这一段网络现在怎么样" 15 秒 这段是链路的"腰部"，变化比区域时延快，但比心跳慢。15 秒能画出有意义的分布，又不至于产生大量请求
④ 节点巡检 "每个中转节点此刻通不通、多快、实际落在哪" 10 秒 1 个 节点数量多，只能轮流。固定节奏（而不是并发）把带宽冲击摊平，也让大屏的"测速中"高亮能按顺序推进
⑤ 手动全速扫描 "我现在就要一份最新的完整结果" 按需触发 排障时不想等一分钟。做法是去掉区域之间的间隔、背靠背连续测，但每个点的采样次数一次不减——快可以，但不能用"少测几次"换速度

8.2 三条"口径"纪律（这是监控可信度的全部）

  1. 同一个数字必须只有一种口径。例如"握手时延"，要么统一用单次 TCP 往返，要么统一用 TCP+TLS 两次往返，不能混着比。 为什么：混口径会让某一条路径天然"少一次往返"，看起来永远最快。曾经出现过"某个地区明显优于其它地区"，实际只是它的测量方式少算了半程。
  2. 无效样本要丢弃，并且丢弃规则要写死。例如低于 10ms 的样本一律视为无效（通常意味着流量走了本机回环或缓存，不代表真实网络）。 为什么：不丢这些样本，"最优值"会被它们永久污染，而且会掩盖真实的网络劣化。
  3. 测不到就显示未测到。不做任何"兜底填充"。 为什么这条是红线：一旦允许"猜一个值填上"，监控就从"事实"退化成"叙事"。真实故障会被填充的数字盖住，排障方向直接跑偏。宁可显示空白，也不显示假数。
反面教材（本项目的真实教训）：探测失败时会话曾经"回填"过一批时间戳，把"从未测到"伪装成"10~50 秒前刚测过"。结果是大屏长期显示绿色的骗人状态，直到有人逐行读脚本才发现。这类"善意的兜底"是监控系统里最危险的东西。

8.3 心跳与"数据年龄"

每条数据都带时间戳，大屏据此计算数据年龄（距离它被真正测出来过了多久），并按颜色分级：

颜色含义你该做什么
绿 新鲜数据在一个正常周期内什么都不用做
黄 偏旧超过正常周期，但还没到"疑似中断"留意一下，可能是网络短暂波动
红 异常从未测到，或远超正常周期按第 12 章排错；红色专留给"未测到/连不上"，不因"数据久"而变红

9.2 合并策略：为什么是"逐字段"而不是"整包"

错误做法：整包取舍

用"这包比上包新吗"来决定整包替换。结果：新包里某个字段恰好缺失，就把上一包里的好数据一起冲掉了。

正确做法：逐字段按时效

每个字段各自带时间戳，谁新用谁。某个字段这轮没上报，就保留它上一次的真实值，直到自己过期。

9.3 一条容易被忽视的硬约束

边缘函数在返回响应之后，未完成的异步工作会被取消。 所以"顺手起一个异步写缓存"这种写法是不安全的——必须 await。表现是"数据时有时无""刷新一下就有了，等一下又没了"，非常难查。

9.4 长轮询为什么比"定时刷新"好

方案数据延迟请求量结论
每 2 秒定时拉平均 1 秒很高（每天每标签页上万次）白耗配额，且数据"一顿一顿"
长轮询接近实时只在有数据时才产生一次往返本项目的选择
服务端推送（SSE/WebSocket）实时最低兼容性与复杂度代价更高，本项目选了长轮询
重试必须退避。长轮询失败后如果固定 200ms 重试，遇到边缘异常时单标签页能打出几十万请求/天。正确做法是指数退避（1s→2s→4s…封顶），成功即复位。

10.4 为什么"节点主动汇报"这件事本身就是设计

  • 不引入入站端口：住宅网络普遍没有公网入口，任何"服务端主动连节点"的方案都需要端口映射或额外穿透。

11大屏：渲染工程学与自愈

大屏是"给人看的事实"。它的难点不在画图，而在一个坏掉的部件不能拖垮整页，以及页面版本必须能自动追上服务端。

11.1 三个必须做到的工程点

  1. 每个渲染器独立隔离。任何一个渲染函数抛异常，只能影响它自己那一块。 为什么：真实教训——一个已被删除的函数仍被调用，抛出的引用错误把它后面所有渲染一起带走，表现为"新鲜度、健康卡、评分、波形全变成 --"。用户看到的是"整页坏了"，实际只有一个函数坏了。所以现在每个渲染器都包在独立的 try/catch 里，错误还会写进隐藏元素，方便事后自查。
  2. 页面版本可自证、可自动追平。服务端每次部署生成新版本号，页面内嵌自己的版本号；两者不一致时页面自动重载。 为什么：否则会出现"用户看到的还是旧界面、你却在看新代码"的鬼故事——排障时最烧时间的一类问题。注意：太旧的页面无法自我更新（它里面还没有这段自更新逻辑），必须手动关掉标签页重开一次。
  3. 前端只写"唯一来源"。同一个指标在整页只允许出现一次、只允许有一个写入点。 为什么：早期同一个数值在多张卡上重复展示，某些卡有真数据、某些卡是写死的旧值，于是"同一页自相矛盾"。删掉重复展示之后，"看起来不对"的地方立刻减少一大半。

11.2 首屏纪律：宁可空着

位置错误做法正确做法
数值型指标HTML 里写死一个好看的数字当占位写 --，等真实数据到达再填
时间型字段初始化成"刚刚"初始化成 0，前端渲染为"未测到"
状态徽标默认显示"全部正常/极优"默认显示"等待数据"，只有真实测到才给结论
榜单/累计值预置一段"历史基数"让曲线好看只认真实累计；没有就是 0
为什么这条要反复强调：占位假值在"一切正常"的时候看起来无害，但恰恰是在出故障的时候最致命——接口全挂时页面依然显示着漂亮的数字，你会以为服务是好的。假数据的成本不是"不准确"，而是"让故障不可见"。

11.3 采集频率的"双模"设计

大屏提供两档：默认「1 分钟采集」与「2 秒极速」。默认档是给日常挂机看的，极速档是排障时用的。关键在于极速档必须由人显式开启，而不是默认行为——否则每个打开的标签页都会持续产生高频请求，把配额吃光。

一个实现细节：极速档下的"槽位对齐抓取"要按墙上时钟对齐到 10 秒边界，而不是"每 10 秒一次"。前者不会随时间漂移，后者会因为每次请求耗时而慢慢跑偏。

12.1 用户端现象

现象最可能的原因怎么确认怎么修

大屏所有数字冻结 节点上"上报脚本"是否在跑；隧道是否存活 节点侧进程被系统杀掉，或隧道断开。看"数据年龄"是几秒还是几十分钟
时延矩阵空白 / 全是未测到 区域测绘脚本是否在跑；落盘文件是否在更新 脚本死了，或单实例锁残留导致新实例起不来
节点矩阵数据明明是旧的，文件时间却在变 结果去重逻辑 去重写成了"保留第一条"→ 新结果被全丢。改为保留最后一条
同一份用户名单在不同入口不一样 权威数据放在哪一层 放在实例内存/机房缓存里，缺少全球权威源（见 7.3）
页面反复自动刷新 三处版本号是否一致 版本注入失败、或页面与接口版本长期不一致
告警横幅一直挂着 节点上报时间戳 节点真断了（先修链路）；或时间戳被错误地初始化成 0 之外的值
点"手动刷新"没反应 指令键是否被写、节点是否取走、是否回执 指令通道断了；或指令"读取即删"导致丢单（见 10.3）
图表空白但其它卡片正常 该图表的数据源接口 取数失败。注意：删掉画布元素会让取数函数抛错并中断整页渲染，所以"不想要的图表"要用隐藏而不是删除
内存/CPU 异常升高、探测频率翻倍 实际在跑的进程数量 看门狗与手工重启同时判断"进程不在"，各拉起一份 → 同一脚本跑 2~3 份。用单实例锁修

14.2 项目里已经形成的约定（照做就不会重犯老错误）

  1. 一个指标只展示一次、只写一个来源。发现重复展示就删掉重复的那一份。
  2. 测不到就留空。不做兜底填充、不做"看起来合理"的估计。
  3. 凡"一个请求写、另一个请求读"的状态，放机房缓存并 await 写入。权威数据放全局存储。
  4. 高频路径上不产生写入。写只发生在"有真实变更"时。
  5. 频率是容量的一部分。加任何周期性动作前，先算它一天会产生多少次请求/多少流量。
  6. 口径唯一定义在采集侧。展示侧不做任何换算，避免两边算法漂移。
  7. 远程控制搭在"节点上报的响应"里，并要求回执。
  8. 改节点脚本必须重启进程；写脚本必须用 LF。
  9. 部署看完整输出、等 30 秒、比三处版本号。
  10. 动手前先备份，且知道怎么回滚。

14.3 四条硬约束（设计的天花板）

① 免费额度

边缘的持久键值存储有每日读写配额（读取宽裕、写入很紧）。整套状态分层设计都是为了不碰这条线。

② 家庭带宽与电量

所有探测/心跳共享同一条家庭上行。能合并的上报必须合并，能降频的必须降频；节点还常是电池设备。

③ 分布式一致性

边缘是分布式的，没有"全局内存"。跨机房要一致，就必须有一个全球权威源。

④ 人的判断力

监控的价值在于"让人能相信它"。一旦出现一次假数据，整块屏的信任就没了——所以宁可空着。

14.4 一句话总览

用户端只做四件事：拿订阅、导入、验证出口、优选接入点。
服务端是三台"机器"的协作：边缘负责分发与聚合，住宅节点负责出口与全部测量，大屏负责把事实呈现给人。
三者之间只有两条通道：节点每几秒一次的主动上报，和浏览器对边缘的长轮询。所有功能——包括远程控制——都建立在这两条通道之上。

文档内所有结论均来自对项目源码、采集脚本与线上运行数据的逐项核对；不含任何真实凭据。
