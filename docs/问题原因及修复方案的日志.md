## 一、 问题根因深度剖析

### 1. KV 读取泄漏根因（每日 ~5.7 万次物理读取）
* **病灶代码：**
  * 手机端 `report_traffic.sh` 原先每 6 秒发起 1 次主请求后，为了让亚洲各机房的观众能读到实时大屏，在后台遍历 `${CF_ANCHOR_4}`、`${CF_ANCHOR_1}`、`${RELAY_TARGET_IP}`，额外发射了 3 次并发 POST。
  * 公式：$(1 \text{ 主} + 3 \text{ 辅}) \div 6\text{s} = 40 \text{ 次/分} = 2,400 \text{ 次/小时} = \mathbf{57,600 \text{ 次/天}}$。
  * Worker 端的 `readCmd(env)` 原实现没有任何内存锁和 `cacheTtl`，对进入 `/api/report_traffic` 的所有请求一律无条件直读 KV：
    ```javascript
    async function readCmd(env) {
      if (!env || !env.SUB_DB) return null;
      try {
        const raw = await env.SUB_DB.get(CMD_KV_KEY); // 物理直读
        return raw ? JSON.parse(raw) : null;
      } catch (e) { return null; }
    }
    ```
* **荒谬之处：** 手机端对这 3 次辅助请求的响应是直接丢弃的（`-o /dev/null`），根本不消费下发的指令。但 Worker 却次次物理直读 KV，单台手机每天白白烧掉 **57,600 次** 读取（占免费额度的 57.6%）。

### 2. KV 写入超额根因（每日 576~900+ 次抢写）
* **病灶代码：**
  * 原 Worker 设置 `SNAP_MIN_GAP_MS = 150000`（2.5 分钟写一次快照），理论底线写入 $1440 \div 2.5 = 576$ 次/天。
  * 但 Cloudflare KV 是“最终一致性”存储，全球节点同步需要最多 60 秒。
  * 手机同时向 4 个机房投递上报，各机房在不同的 Worker Isolate 中运行。机房 A 刚写入快照，机房 B 读到的仍然是滞后的计数器，误判为“上一机房失联”，随即发生抢写。
  * 最终真实写入突破 `SNAP_DAILY_CAP = 900` 熔断线，频繁打爆 Cloudflare Free 的 1,000 次/天硬限制，挤占了修改用户、配置同步和手动测速的所有写入余量。

### 3. Worker 请求数瓶颈
* 4 路并发每 6 秒产生 57,600 次 Worker 请求，直接吃掉 10 万总额度的 57.6%，彻底锁死了接入“甲骨文免费服务器作为第二个出口节点”的扩展空间。

## 二、 修复方案（方案 2+ 极致增强版）

### 1. 核心架构：10 秒单种子轮巡 + 主辅载荷解耦
* **节拍谐振：** 手机端测速槽位（`ping_scheduler.sh`）本身就是 10 秒一个区域。将上报周期统一为 **10 秒**，实现物理谐振。
* **单种子轮巡：** 手机不再并发发射 3 个种子，而是每 10 秒只发射 1 个种子，依次推进：
  * 第 0 秒：主请求 + 种子 1（POP1 吉隆坡）
  * 第 10 秒：主请求 + 种子 2（POP2 香港）
  * 第 20 秒：主请求 + 种子 3（POP3 新加坡/东京）
  * 第 30 秒：主请求 + 种子 1（循环）
  30 秒即可完成亚洲核心机房全覆盖，远低于大屏 60 秒失效阈值。
* **极速轻量通道 (`?seed=1`)：** 辅助请求带上 `?seed=1` 标签。Worker 收到后：
  1. 仅写入本机房 `caches.default.put('stats_latest')` 供大屏秒开；
  2. 完全跳过 `readCmd`（0 读 KV）；
  3. 完全跳过 `SNAP_KV_KEY` 评估与写入（0 写 KV）；
  4. 完全跳过用户库版本核对与主库合并；
  5. 立即返回 `204 No Content`，执行耗时 < 2ms。
* **主辅动态容灾：** 如果手机主请求因默认国际路由抖动失败，当期的种子请求自动“升格”为主请求，带回全量配置与指令，杜绝控制面单点故障。
* **KV 内存防抖锁：** 在 `readCmd` 中加入 10 秒内存时间锁，并在 `writeCmd` 与 `clearCmd` 时主动更新/清理内存缓存。
* **全局快照步长收敛：** 将快照间隔放宽至 **8 分钟（480 秒）**，硬上限设为 **250 次**。每天理论写入仅 180 次，释放 820+ 次安全余量给正常业务。

## 五、 前端大屏遥测推送中断误报根因与多阶色彩重构

### 1. 现象与误报根因
* **表象：** 浏览器大屏标题栏频繁闪烁红字 `⚠️ 遥测推送中断 15 秒`，而卡片正文却显示绿字 `🟢 16秒前数据`，两者逻辑矛盾。
* **病灶代码：**
  * 服务端 `/api/live` 长轮询的设计为：在没有新数据时挂起等待最多 15 秒（`while ((Date.now() - t0) < 15000)`）。
  * 前端 `updateLiveTag` 却将中断判定硬编码为 `isLive = hasPush && ago < 15`。
  * 每次长轮询等待到 14~15 秒正常返回时，前端本地计时器恰好到达 15 秒，导致每次正常轮询周期都会瞬间触发红色虚假报警。

### 2. 多阶健康状态重构方案
依据用户明确指定的 4 阶健康阈值重构 `updateLiveTag()`：
* **$\le 40$ 秒（健康）：** 绿色（`#22c55e`）—— 显示 `⚡ 遥测推送 刚刚 / X 秒前 · 数据 Y 秒前 · 版本 ...`
* **$41 - 70$ 秒（正常）：** 蓝色（`#38bdf8`）—— 显示 `⚡ 遥测推送 X 秒前 · 数据 Y 秒前 · 版本 ...`
* **$71 - 99$ 秒（轻微延迟/更新中）：** 黄色（`#eab308`）—— 显示 `⏱ 遥测更新中 · X 秒前 · 数据 Y 秒前 · 版本 ...`
* **$\ge 100$ 秒（中断）：** 红色（`#ef4444`）—— 显示 `⚠ 遥测推送中断 X 秒 · 版本 ...`

### 3. 执行结果
* 线上边缘 Worker 已全量编译并部署（`BUILD_ID=b20261008-185935`），经实测 200 OK 且 4 阶颜色逻辑全部生效。
* GitHub 仓库代码已通过最小行列差异精准合入。

## 六、 冗余卡片剔除与大屏总流量统计严重失真根因及修复

### 1. 冗余卡片剔除
依据用户指令，彻底移除大屏第 2.5 栏的两张历史卡片：
1. **本机接入质量评分（6个CF锚点综合）**（`qualityScore`、`qualityGrade`、`qualityBar`、`qualityDetail`）
2. **上报链路可靠性（上报延迟评分、手机上报节奏、本轮采样覆盖）**（`relReport`、`relCover`、`relNote`）
* 前端底层 JS 对这些元素均有安全存在性判断（`if (el)`），移除卡片 DOM 后不影响任何后台测速算法与逻辑。

### 2. 网页大屏总流量统计严重失真根因深度剖析
* **表象矛盾：** 手机端持久化基线 `user_traffic_base.txt` 显示各用户物理累计流量已达 **~39.0 GB**（例如 `c7lbf71z` 达 27.9 GB，`k12ids6z` 达 5.2 GB），但网页大屏总流量却长期卡在 **9.83 GB**（`c7lbf71z` 显示 4.4 GB，`k12ids6z` 显示 0 B）。
* **病灶代码定位：**
  * 在手机端 `report_traffic.sh` 第 437 行的 awk 脚本中，残留了一段打印指令：
    ```awk
    printf "\n#ONLINE#";
    for (t in online_set) { ... }
    printf "\n";
    printf "\"userTraffics\":{";
    ```
  * awk 脚本的标准输出被整体赋值给变量 `USER_TRAFFICS_JSON`；
  * 当手机端触发重载荷（12 小时定时或版本变动）上报时，`echo "{$TELEMETRY_JSON ... $USER_TRAFFICS_JSON ...}"` 生成的 `traffic_payload.json` 内部被直接插入了未带引号与键名的字面量字符串 `\n#ONLINE#c7lbf71z\n`！
  * **后果：** 导致重载荷 JSON 发生致命语法错误（`JSONDecodeError`）。Cloudflare Worker 收到后 `await request.json()` 解析失败抛出异常，导致**手机上报的最新全量用户累计流量自 10 月 4 日起从未成功落库**，Worker 只能持续沿用 10 月 4 日的 9.83 GB 历史遗留快照！

### 3. 修复方案与闭环验证
1. **手机端修复：** 彻底剔除 `report_traffic.sh` awk 块内破坏 JSON 结构的 `#ONLINE#` 打印语句，重载荷生成的 `traffic_payload.json` 恢复为 100% 合法 JSON；
2. **实时同步推送：** 将更新后的脚本推送至手机，执行重载荷上报；
3. **数据校验结果：**
   * `/api/stats_data` 成功刷新：下行流量恢复为 **37.1 GB**，上行回传 **1.92 GB**，总吞吐量矫正为 **39.02 GB**！
   * 各用户全周期累计流量恢复真实数值：`c7lbf71z`（27.95 GB）、`k12ids6z`（5.24 GB）、`8arg0wtb`（3.02 GB）、`e35edips`（1.15 GB）、`ipol3b4o`（1.13 GB）、`oe12xaft`（470.8 MB）、`0y8x0k3g`（54.1 MB）；
4. **大屏联动增强：** 在前端 `applyBwPanel()` 内将 `totalBytes`、`downBytes`、`upBytes` 与实时推送联动，大屏卡片 4 与顶部仪表盘实现秒级同频刷新。

## 七、 方案 A 实施：美国洛杉矶 1Gbps 独立出口节点上线与双活集群聚合

### 1. 架构目标与技术选型
* 为弥补纯手机出口在超大文件下载、高峰期 4K 播放场景的并发与带宽上限，引入一台独立公网 IPv4 的美国洛杉矶 VPS（Debian 12, 1 vCore, 2GB RAM, 1Gbps 端口, 2TB 流量）。
* **协议决策：** 选用 **VLESS + Reality（TCP/xtls-rprx-vision）** 架构。
  * 相比于套 Cloudflare 隧道方案，Reality 直连方案彻底解除了 Cloudflare 免费 CDN 对长连接的 QoS 限速，可跑满千兆带宽（~1Gbps）；
  * 零域名、零证书依赖，借助权威大厂 SNI 握手伪装（`gateway.icloud.com`），抗 GFW 主动探测能力极强。

### 2. 部署与接入落地
1. **VPS 节点初始化：**
   * 开启 Linux BBR 拥塞控制与 FQ 排队规则；
   * 安装官方最新 Xray-core（v26.3.27），监听 443 端口；
   * 生成 Reality 密钥对并注入系统权威用户库（全部 11 个用户 UUID 同步授权）；
   * 服务状态自启常驻运行（`active (running)`）。
2. **边缘 Worker 订阅聚合更新：**
   * 在 `/sub` 订阅生成器中，将美国节点 `🇺🇸 美国-洛杉矶 1Gbps` 注入到 Clash 配置（`proxies`、`PROXY` 策略组、`AUTO - 自动选优`、`FALLBACK - 故障转移`）以及 V2Ray / Base64 订阅链接中；
   * 客户端在拉取订阅时，自动携带当前用户的专属 UUID，实现全用户无感知双出口平滑切换与负载均衡。
3. **验证结果：**
   * Clash YAML 与 V2Ray 节点均已成功注入美国高速出口；
   * 外网 TCP 443 端口测试直通（`TcpTestSucceeded: True`），中美直连低延迟通信正常。
