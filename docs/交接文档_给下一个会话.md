## 4. 今天已修复的重大问题（都经过实测验证）

### 4.1 KV 超额（最初的问题）
- **根因**：手机每次上报都 `db.put('stats:latest')`（约 15,000 次/天）+ 每次 `/admin` 都 `db.list()`
- **修法**：所有实时数据移到内存 + Cache API；KV 只留用户库
- **现状**：read 1,308 / write 4 / list 1（对比 10-01 的 write 1,905 超限）

### 4.2 跨 isolate 状态不一致（**本项目的头号陷阱，今天踩了 7 次**）
**Workers 的模块级变量是每个 isolate 私有的**，同一机房有多个 isolate，不同机房更是各有各的。
手机上报落在一个 isolate，大屏查询常落另一个 → 读到 null 或旧值。

已修复的 7 处：
1. 用户库（`globalMemoryUsers`）→ Cache API + KV
2. 遥测快照（`globalMemoryStats`）→ Cache API，且 `/api/stats_data` 改为**缓存优先**
3. `phoneMasterInfo`（手动刷新确认）→ Cache API
4. 缓存写入用了 fire-and-forget → **Worker 会在响应后取消未完成的异步工作**，必须 `await`
5. 合并策略用 `reportedAt` 做**整体取舍** → 丢确认；改为**逐字段按各自时效合并**
6. 以 isolate 内存为基底覆盖共享缓存 → 抹掉确认；改为**以共享缓存为基底**
7. `payload.syncRequest` 回退到 `syncReqMemory`（isolate 私有）→ 复活已消费指令；**已彻底移除该回退**

**统一辅助层（已就位，新代码请复用）**：
```js
await cacheGetJson(name)          // 读同机房共享缓存
await cachePutJson(name, obj, ttl)  // 写, 必须 await
```
**规则：凡"一个请求写、另一个请求读"的状态，一律走这两个函数。**

### 4.3 假数据（用户最在意的"真实性"）
| 位置 | 假在哪 | 修法 |

| 带宽波形 | `0.25 + (字节%5)*0.05` 凭空造数 | 已删除，如实上报 |
| 六大地区兜底 | 假延迟 186/140/213/192 + 假电量/WiFi | 已清空 |

| 水位计 | 满刻度 64 但标注"警戒阈值 500" | 已统一为 500 + 显示近15分钟峰值 |

### 4.4 六大地区测试时间不准（用户反复反馈）
| 问题 | 根因 | 修法 |
|---|---|---|
| 年龄显示 1~7 秒循环 | 测的是"浏览器上次轮询"而非数据年龄 | 改用真实 `pingTimes` |
| 年龄虚增 60 秒 | 每区域时间戳只在 60 秒轮询时更新，实时推送没带 → 本地耗时累加 | 推送快照带上 `pingTimes`/`pings`/`serverTime` |
| 出现 102/92/82/72 秒 | 槽位跳过（单次迭代越过 10 秒边界，整轮跳过） | 周期锚定"墙上时钟整分钟"，物理上不可能漂移 |
| 6 区域时间戳完全相同 | `NOW` 在 for 循环外只取一次 | 每区域重新取 `NOW` |

**现状**：周期锚定整分钟，6 区域落在 -2/8/18/28/38/48 秒，10 次采样，最大年龄约 58 秒。

## 5. 手动刷新（已实现，端到端验证过一次）

```
点按钮 → POST /api/manual_scan → Worker 写 KV flag
      → 手机下次上报(约6秒)拿到 → report_traffic 落 scan_req 标记
      → ping_scheduler 启动 fast_scan.sh → 6 区域背靠背(去掉10秒间隔, 仍10次采样)
      → 每测完一个立即落盘 → 上报 → 大屏逐个点亮
```

**实测（2026-10-03 22:38）**：6 区域相邻间隔 **2~3 秒**、总耗时 **14 秒**（常规是 60 秒）✅

**注意**：`fast_scan.sh` 是**独立进程**，不改动 `ping_scheduler` 的槽位时序（避免破坏已稳定的调度）。

## 6. 关键操作经验（**踩过的坑，务必遵守**）

### 部署类
1. **部署输出绝对不能截断** —— 我因为一直 `Select-Object -Last 1`，把错误信息也截掉了，导致误判"已成功"很久
2. **部署后至少等 20~30 秒再查线上版本** —— 等 6~8 秒会读到上一个版本
3. **判断部署是否生效**：比对三处 `BUILD_ID`（源码 / `/api/live` / 页面内嵌 `window.__pageBuild`）
4. `cf_deploy.py` 每次自动注入新 `BUILD_ID`；页面数字不同会自动重载
5. **旧页面无法自我更新** —— 页面版本如果早于 `checkPageBuild` 修复，必须手动关标签页重开

### 手机脚本类
6. **部署手机脚本后必须重启进程** —— 进程启动时读取脚本，改文件不重启无效
7. **adb shell 脚本必须是 LF 换行**（CRLF 会报 `syntax error`），用 `write` 工具写文件是 LF ✓
8. **`pkill -f xxx` 之后要确认谁负责重启它** —— 我杀掉 `traffic_daemon.sh` 后无人复活，服务中断
9. **看门狗顺序**：先杀 `traffic_daemon.sh`（否则它不断复活子进程），再杀其余，最后只起一个

### 诊断类
10. **`pgrep -f foo` 会匹配到你自己那条含 "foo" 的命令行** → 误报"重复进程"。用 `ps -A -o PID,PPID,ARGS` 精确判断
11. **PowerShell 内联 Python 会被吃掉引号/`$`** → **一律用 `write` 工具写 .py 文件再执行**
12. `Get-Date -UFormat %s` 返回的是**本地时区偏移后的时间**（+8h），别用它跟 Unix 时间戳比

### DSH / AA 类
13. **绝不在会话内重启 DSH**（会终止对话）
14. **AA Desktop 用 `Start-Process` 起不来**（启动上下文问题），必须：
    ```powershell
    Start-Process explorer.exe -ArgumentList '"Z:\AGENTS\Agents Anywhere\Agents Anywhere.exe"'
    ```
15. AA 体检：`powershell -ExecutionPolicy Bypass -File "C:\Users\SURFACELAPTOP STUDIO\Desktop\agents-anywhere-setup\aa_status.ps1"`
